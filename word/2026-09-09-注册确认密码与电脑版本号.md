# 注册确认密码、电脑版本号与邮箱验证评估

## 用户要求与实现

- 注册时新增必填的“确认密码”，两次密码逐字符一致才发送创建账号请求；不一致显示明确错误。切换登录/注册时清空确认密码，请求中禁止切换模式。
- 确认密码属于输入防误操作校验，保留原注册 API 的 email/password/name 请求契约，兼容旧缓存 Web 和 Windows/Android 0.4.x；未把确认密码保存到设备或传给服务端。
- Windows 客户端左上角系统标题栏显示“记时 v实际安装版本”。远程页面从 JishiWindows User-Agent 读取版本并更新 document.title，不使用更新清单中的最新版本冒充本机版本。登录页与主界面均生效。
- 原生壳、主机解析、离线页未修改；Windows 保持 0.4.5，Android 保持 0.4.6。完全离线、无法加载远程页面时仍使用原安装包的标题。本次重新生成 Web releaseId/webBuild。

## 邮箱验证码注册可行性

结论：现有 Worker/D1 结构可以增量接入，改动规模中等；不是只加输入框即可安全上线。此次仅评估，未启用邮箱验证或发送邮件。

现状：server/src/index.ts 的 register 校验邮箱格式、密码长度、邮箱是否重复，然后写入 users/auth_credentials 并签发登录 Cookie。Env 只有数据库、媒体、来源与认证密钥配置；仓库未发现发信服务、验证码表、发送接口或频率限制。

建议实施范围：

1. 配置一个可用的事务邮件 HTTP API 与已验证发信域名，密钥只放生产秘密配置。以 Resend 为例，发信域名需要 SPF 和 DKIM 验证，见官方文档 https://resend.com/docs/dashboard/domains/introduction 。本次未确认用户是否已开通发信服务。
2. 新增编号迁移，保存绑定邮箱及注册用途的验证码摘要、到期时间、失败次数、已消费状态；不保存明文验证码。建议初始有效期 10 分钟、重发间隔 60 秒，并增加邮箱/IP 限流及全局发送预算。
3. 新增验证码发送接口；错误、过期、重复使用必须拒绝，正确验证码的消费与创建账号须原子完成，避免并发复用。发送失败返回明确 JSON，不能留下半注册账号。
4. 注册页添加验证码与重发倒计时；密码确认继续保留。已有账号登录无需补验证码，已有会话不失效。
5. 强制验证码时不能为“旧客户端”保留绕过验证的注册入口，否则无法保证“验证后才能注册”。旧注册路径保留，对缺少验证码的旧缓存页面返回可识别的 JSON 提示并引导刷新；正式开启强制验证前需明确接受这个注册行为变化并验证旧 PWA 更新。
6. 联调常见邮箱收件、垃圾箱、超时、重发、暴力尝试、并发消费、重复邮箱、旧客户端登录与注册提示。

工程估时（基于当前代码的估计，并非服务商承诺）：已有可用发信配置时约 1–2 个工作日完成开发和联调；从零开通与域名验证再预留约 0.5–1 个工作日操作时间，DNS 生效、服务审核和送达率调试可能延长。需先确定发信服务及域名访问权限。
